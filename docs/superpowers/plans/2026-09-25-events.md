# Events Implementation Plan

**Goal:** Deliver the events module described in
`docs/superpowers/specs/2026-09-25-events-design.md`: categories, events and
their check-in sessions, registration with fee tiers, a payment ledger, a
run-of-show program timeline, and a planning checklist.

**Shape:** Six PRs, one per phase. Each phase starts from a fresh branch and
worktree off `origin/main` (`irm new feat/events-<phase> events-<phase>`) and
merges before the next phase that depends on it. Phases 2, 4, and 5 depend
only on phase 1, which ships the shared `MemberPicker` and `MoneyInput`.
Phase 3 depends on phase 2.

**Acceptance tests first.** The spec's §9.1 table (A1–A11, S1–S5, C1, K1–K4,
L1–L5) assigns each test to a phase. Write the phase's tests before its
implementation. They start failing, and the phase is done when they pass.

## Global constraints

Read these before every phase:

- **Next.js 16 is modified.** Before writing pages or actions, read
  `node_modules/next/dist/docs/01-app/` on server actions, dynamic routes and
  layouts. Mirror working files instead of guessing.
- **Storybook comes first.** Build each component and its `*.stories.tsx`
  with fixtures, check both themes and a narrow width, and only then wire it
  into a route. Stories import no server code. Server actions are injected
  props, or stubs in stories.
- **Forms** follow `service-form.tsx` + `services/actions.ts`:
  `requirePermission` first, then zod via `lib/validators.ts`, then
  `fieldErrors`, `revalidatePath`, and `redirect`. Each input sits in
  `<Field htmlFor>`.
- **Tables** follow `app/(app)/members/page.tsx`: `tableContext` with
  `sortKeys`, an `orderBy` that ends with `id`, `allowedValues` on every facet,
  and `overRunPage` + `redirect`.
- **Times** go through `lib/manila-time.ts`. Never call `new Date(formValue)`.
- **Money** is integer centavos, parsed and formatted only through
  `lib/money.ts`.
- **Colours** come only from tokens. `tests/ui/design-tokens.test.ts` must stay
  green.
- **Scope every id to its event.** Load child rows with
  `WHERE id = $1 AND event_id = $2`, where `$2` is the event in the URL.
  A mismatch is "not found" (spec §6, test C1).
- **Permissions:** a new key goes in `lib/permissions.ts` and in the same
  phase's migration, with grants per spec §6, following
  `docs/authorization.md`.
- **Migrations:** `bun run db:generate --name <name>` for DDL. For
  permission and category rows, add `bunx drizzle-kit generate --custom --name
  <name>` and write the `INSERT … ON CONFLICT DO NOTHING` by hand, the way
  `0005` does. Run `bun run db:migrate` locally. Never `db:push`.
- **Checks before each PR:** `bun test lib`, `bun run test:ui`,
  `bun run lint`, `bun run build`, `bun run build-storybook`, then
  `bun run test:db:up`, `bun run test:integration` and `bun run test:e2e`, run
  one after another. The PR description lists which states were checked
  visually in Storybook.

## Phase 1: Events core

**Branch:** `feat/events-core`

### 1.1 Pure foundations

- [ ] `lib/manila-time.ts` + `lib/manila-time.test.ts`:
      `parseManilaDateTime`, `toManilaDateTimeInput`, `parseManilaDate(value,
      "start" | "end")`, `manilaDayKey`, `eachManilaDay`. Use a fixed `+08:00`
      offset: the Philippines has no DST, and an explicit offset avoids
      depending on the ICU data in the process. Tests run under `TZ=UTC` and
      `TZ=America/New_York` and must produce the same instants.
- [ ] `lib/events.ts` + tests: `eventPhase`, `formatEventRange`
      (same-day, multi-day, all-day, cross-month, cross-year), and
      `registrationState` (stubbed here, completed in phase 2).
- [ ] `lib/constants.ts`: `EVENT_STATUSES`, `EVENT_CATEGORY_COLORS`, the
      `EVENT_PHASES` labels, and `SYSTEM_EVENT_CATEGORIES` (ids, names, colours,
      `registration_default`).

### 1.2 Schema and migration

- [ ] `db/schema.ts`: `eventCategories`, `events`, and `services.eventId` with
      `services_event_id_idx`, plus relations and types.
- [ ] `bun run db:generate --name events_core`.
- [ ] Custom migration `events_core_data`: the seven system categories, the
      permission rows `events.view|create|update|delete|manage_categories`, and
      grants (admin: all; leader: view, create, update; usher: view).
- [ ] `lib/permissions.ts`: add the `events` module and five keys. Update
      `lib/permissions.test.ts` and `tests/integration/permissions.test.ts`.
- [ ] `db/seed.ts`: one upcoming camp (three days, three sessions), one past
      retreat with attendance, and one cancelled outreach.

### 1.3 Validators

- [ ] `eventSchema`: name, `categoryId`, `allDay`, start/end, location,
      description, notes, and the `registration*` fields and `capacity`, which
      parse in phase 1 but are hidden in the UI until phase 2. Rules: the end is
      not before the start, and the capacity is a positive integer or null.
- [ ] `eventCategorySchema` and `sessionSchema` (name, a Manila datetime within
      the event's day range).
- [ ] Cases in `lib/validators.test.ts`.

### 1.4 Components (Storybook first)

- [ ] `components/patterns/section-tabs.tsx` + story + `tests/ui` test
      (`aria-current`, hidden tab, overflow at 360px).
- [ ] `components/events/event-category-badge.tsx` + story (every colour in
      both themes).
- [ ] `components/events/event-phase-badge.tsx` + story.
- [ ] `components/events/event-form.tsx` + story (create, edit, all-day,
      errors, pending). Uses `FormSelect` for the category and `DatePicker` or
      datetime inputs for dates.
- [ ] `components/events/event-sessions-card.tsx` + story (empty, populated,
      read-only). Includes an "Add session" form and an "Add one per day" form
      (time of day).
- [ ] `components/events/event-category-form.tsx` + story.
- [ ] `components/form/member-picker.tsx` + story + UI test. It is built on
      Base UI `Combobox`, takes `search: (q) => Promise<{ id, name, status,
      disabledReason? }[]>`, and debounces by 200ms with a minimum of 2
      characters. It posts the chosen id in a hidden input named by `name`,
      and forwards `aria-describedby` and `aria-invalid` the way `FormSelect`
      does. It is shipped here because phases 2, 4, and 5 all use it.
- [ ] `components/form/money-input.tsx` + story (a `₱` prefix,
      `inputMode="decimal"`), together with `lib/money.ts` + tests
      (`parsePesos` accepts "1500", "1,500", "1,500.5", "₱1,500.50" and rejects
      negatives, more than two decimals, and junk; `formatPeso`;
      `sumCentavos`).
- [ ] `app/(app)/members/search-action.ts`: `searchMembers(q, { eventId? })`.
      It requires `members.view` **or** `events.register` (the key exists

- [ ] `docs/design-system.md`: add `SectionTabs`, `MemberPicker`, and

### 1.5 Routes and actions

- [ ] `app/(app)/events/actions.ts`: `createEvent`, `updateEvent`,
      `setEventCancelled`, `deleteEvent` (spec §7 guards: refused while any
      session has attendance; otherwise deletes its sessions and then the
      event, in a transaction), `addSession`, `addSessionPerDay` (idempotent:
      skips a day that already has a session at that time), and `removeSession`
      (refused while the session has attendance).
- [ ] `app/(app)/events/categories/actions.ts`: create, update, set active,
      and delete (refused for a system category or one in use).
- [ ] `app/(app)/events/page.tsx`: the `DataTable` (spec §8.3; the
      registered and outstanding columns arrive in phases 2–3).
- [ ] `app/(app)/events/new/page.tsx` and `[id]/edit/page.tsx`.
- [ ] `app/(app)/events/[id]/layout.tsx`: the header and `SectionTabs`.
      Only Overview exists yet; the other tabs are added by their own phases.
- [ ] `app/(app)/events/[id]/page.tsx`: Overview with details, sessions, and a
      unique-attendees stat (`COUNT(DISTINCT member_id)` over the sessions).
- [ ] `app/(app)/events/categories/page.tsx`.
- [ ] `components/app-sidebar.tsx`: an Events item (`CalendarRange` icon,
      `events.view`). Update its story.
- [ ] `/scan` picker: left-join `events` and label the session "Event ·
      Session". Update `lib/scan-selection` tests if the shape changes.
- [ ] `/services/[id]`: a "Part of …" link when `eventId` is set, and a
      banner when the event is cancelled.
- [ ] **Session guards in the existing modules** (spec §7.4):
      `deleteService` refuses an event session that has attendance, and
      requires `events.update` in addition to `services.delete` for event
      sessions. `updateService` keeps a session within the event's days.
      `recordAttendance` and every other attendance-writing action refuse
      a session whose event is cancelled. `/scan` hides cancelled events'
      sessions from the picker, but that is only the UI half.

### 1.6 Tests

- [ ] Integration: the create → sessions → check in → unique-attendees flow,
      `addSessionPerDay` idempotency, the permission guard on each action,
      and acceptance tests **K1–K4**, **L2** (sessions part), and **C1**
      (sessions).
- [ ] E2E: create a three-day camp, add a session per day, and see Day 1 in
      the `/scan` picker. Cancel the event and check that a
      `/scan?service=` deep link refuses check-in (K3).

**Done when** an admin can create, edit, cancel and delete events, manage
categories, and add sessions that appear in `/scan`; an usher can only view
them; and no path through `/services` or `/scan` can delete attended sessions
or check in to a cancelled event.

## Phase 2: Registration and fees

**Branch:** `feat/events-registration`

### 2.1 Logic

- [ ] `lib/events.ts`: finish `registrationState` (including `cancelled`,
      `no_fee_offered`, and the null close time meaning the event end), and
      add `offeredFees` and `defaultFee`. Tests cover a cutoff that is exactly
      now, all tiers expired versus no tiers (**A11**), and an ongoing event
      (**L4**).

### 2.2 Schema and migration

- [ ] Add `eventFees`, `eventRegistrations` (`charge_centavos` and
      `retained_centavos`), and `eventRegistrationChargeChanges` (spec
      §4.4–4.5), with a unique `(event_id, member_id)` and indexes.
- [ ] Custom migration: `events.register` and `events.adjust_amount`, with
      grants per spec §6.
- [ ] Constants: `REGISTRATION_STATUSES`. Seed: tiers on the camp and 10
      registrations, one of them waitlisted.

### 2.3 Validators

- [ ] `feeSchema` (label, amount via `parsePesos`, optional `availableUntil`).
- [ ] `registrationSchema` (`memberId` **or** a nested visitor, `feeId`,
      notes).
- [ ] `visitorSchema` (first and last name required, contact optional). It
      builds `fullName` the same way the member form does.
- [ ] `changeFeeSchema` and `adjustChargeSchema` (a required reason) and
      `cancelRegistrationSchema` (retained amount between 0 and the charge; a
      reason is required when it is above 0).

### 2.4 Components

- [ ] `components/events/fee-tiers-card.tsx` + story.
- [ ] `components/events/register-form.tsx` + story (a member, a visitor, no
      fees, a waitlist notice).
- [ ] `components/events/registration-status-badge.tsx` + story.
- [ ] `components/events/charge-history.tsx` and
      `cancel-registration-dialog.tsx` + stories. The retained-amount field is
      shown only with `events.adjust_amount`.

### 2.5 Routes and actions

- [ ] `searchMembers`: accept `events.register`, and flag members already
      registered for `eventId`.
- [ ] Event actions: `addFee`, `updateFee`, and `setFeeActive` (a fee with
      registrations can only be deactivated).
- [ ] `app/(app)/events/[id]/registrations/actions.ts`:
    - A shared `withEventSeatLock(eventId, fn)` helper: open a transaction,
      run `SELECT … FOR UPDATE` on the event row, and pass the locked event
      and a fresh registered count to `fn` (spec §7.1). **Every seat-changing
      action uses it:** `registerMember`, `reactivateRegistration`,
      `promoteFromWaitlist`, `cancelRegistration`, and `updateEvent` when
      capacity changes. `setEventCancelled` uses it too.
    - `registerMember`: inside the lock, check `registrationState`, check
      that the fee belongs to this event and is offered, create the visitor
      member if needed (`status: "visitor"`, a `qrToken` as the members
      action does until #17 lands), and reactivate a cancelled row or insert
      a new one as `registered` or `waitlisted`. The charge is snapshotted
      from the fee.
    - `changeFee` and `adjustCharge` (`events.adjust_amount`): update the
      charge and insert a charge-history row in one transaction.
    - `cancelRegistration`: a retained amount of 0 needs `events.register`,
      and more than 0 needs `events.adjust_amount`. It never auto-promotes
      anyone.
    - `promoteFromWaitlist`: refused while full, unless `override=1` **and**
      `events.update`.
- [ ] Show the registration settings in `EventForm` and on the edit page.
- [ ] `[id]/registrations/page.tsx`: the `DataTable` (payment columns arrive
      in phase 3) and the tab in the layout, hidden only when registration is
      disabled **and** no registrations exist (**L3**).
- [ ] `[id]/registrations/new/page.tsx` and `[id]/registrations/[regId]/page.tsx`.
- [ ] Overview: add a registered/capacity stat and the fee tiers card.
- [ ] `/events` list: add a registered/capacity column.

### 2.6 Tests

- [ ] Integration: acceptance tests **S1–S5**, **A2** (permission part),
      **A10**, **A11**, **L4**, and **C1** (fees and registrations); plus
      re-registration reactivating the row, the visitor path creating a
      member with status `visitor`, and the permission guards.
- [ ] E2E: register an existing member, and register a new visitor.

**Done when** staff can set tiers and capacity, register members and new
visitors, and see a waitlist form at capacity, with charges snapshotted,
every charge change logged, and every seat change serialised.

## Phase 3: Payments

**Branch:** `feat/events-payments`

- [ ] `lib/event-payments.ts` + tests: `effectiveAmountDue`, `settle`,
      `paymentStatus`, and `eventFinanceSummary` (spec §3.3 and §5). Unit
      tests: **A1, A3, A4, A5**, all payments voided, and a refund that
      brings the refund due back to 0.
- [ ] Schema: `eventPayments` (spec §4.6), with a unique `submission_id`.
      Custom migration: `events.record_payment` and `events.void_payment`,
      with grants.
- [ ] Constants: `PAYMENT_METHODS`. Validators: `paymentSchema` (a
      **positive** amount, reference required for `gcash` and
      `bank_transfer`, `paidAt` not in the future, `submissionId` a UUID),
      `refundSchema` (a positive amount that the action negates, and a
      required reason), and `voidSchema` (reason required).
- [ ] Components with stories: `payment-status-badge.tsx`,
      `payment-ledger.tsx` (voided rows struck through and marked "Voided",
      not only by colour; refunds labelled), `record-payment-form.tsx` (amount
      defaults to the balance), and `void-payment-dialog.tsx`.
- [ ] Actions: `recordPayment` (`events.record_payment`, positive only),
      `recordRefund` (`events.void_payment`, stores the negated amount), and
      `voidPayment`, which runs `UPDATE … WHERE voided_at IS NULL` and treats
      0 rows as "already voided". Inserts use
      `ON CONFLICT (submission_id) DO NOTHING` and return the existing row on
      a retry. The registration is loaded scoped to the URL's event. There is
      no update or delete action for payments.
- [ ] `deleteEvent`: extend the guard so that any payment row (voided
      included) or charge-history row blocks deletion (**L1**).
- [ ] Registration detail: the ledger, the charge history, outstanding or
      refund due, the payment and refund forms, and a `submission_id` hidden
      input rendered fresh on each page load.
- [ ] Registrations table: charge, effective amount due, paid,
      outstanding/refund due, and payment status columns, plus a payment
      status facet. The facet is computed with a
      grouped subquery, so the filter and sort run in SQL, not in JavaScript.
- [ ] Overview: charged, collected, outstanding, and a "Refunds due" stat
      when greater than 0, all **summed per registration**. When the event is
      cancelled, the overview also lists who is owed a refund. `/events`
      list: outstanding and refunds-due columns.
- [ ] CSV export `app/(app)/events/[id]/registrations/export/route.ts`
      (`events.view`), with one row per registration and amounts in pesos.
      Name the helper after the #26 pattern so the issue can reuse it.
- [ ] Integration: acceptance tests **A1–A9** and **L1**, and **C1**
      (payments).
- [ ] E2E: record a partial GCash payment and see the outstanding balance on
      the overview.

**Done when** the registration desk can take payments, admins can void or
refund them, and every balance on screen is derived from the ledger.

## Risks

| Risk | Mitigation |
| --- | --- |
| The Manila-time helper diverges from the existing services code, which still uses the process time zone | Scope the fix to events and file a separate issue for services and occurrences. The integration test for the `/scan` label asserts Manila wall time. |
| The capacity race under the transaction pooler | Postgres `SELECT … FOR UPDATE` works in transaction mode, and the integration test runs two actions in parallel. |
| `MemberPicker` search floods the database | 200ms debounce, a minimum of 2 characters, 20 results, and the `members_full_name_idx` index already exists. `ilike '%q%'` cannot use a btree index; if it is slow at real sizes, add `pg_trgm` later. |
| Visitor rows fill the directory | They are status `visitor` and already facetable. Merging duplicates is out of scope. |
| QR removal (#17) touches `members.qrToken`, which visitor creation writes | Visitor creation calls the same helper the member form uses, so #17 changes one place. |
