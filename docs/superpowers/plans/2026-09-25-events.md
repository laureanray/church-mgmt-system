# Events Implementation Plan

**Goal:** Deliver the events module described in
`docs/superpowers/specs/2026-09-25-events-design.md`: categories, single-day
events with their own attendance and check-in from `/scan`, registration with
fee tiers, a payment ledger, a run-of-show program timeline, and a planning
checklist.

**Shape:** Six PRs, one per phase. Each phase starts from a fresh branch and
worktree off `origin/main` (`irm new feat/events-<phase> events-<phase>`) and
merges before the next phase that depends on it. Phases 2, 4, and 5 depend
only on phase 1, which ships the shared `MemberPicker` and `MoneyInput`.
Phase 3 depends on phase 2.

**Acceptance tests first.** The spec's §9.1 table (A1–A11, S1–S5, C1,
K1–K5, L1–L7, M1, AU1–AU2, SE1, P1) assigns each test to a phase. Write the phase's tests before its
implementation. They start failing, and the phase is done when they pass.

## Global constraints

Read these before every phase:

- **Next.js 16 is modified.** Before writing pages or actions, read
  `node_modules/next/dist/docs/01-app/` on server actions, dynamic routes and
  layouts. Mirror working files instead of guessing.
- **Storybook comes first.** Build each component and its `*.stories.tsx`
  with fixtures, check both themes and a narrow width, and only then wire it
  into a route. Stories import no server code. Server actions are injected
  props, or stubs in stories.
- **Rules live in `server/`, following `server/members.ts`.** Every
  mutation and query named in this plan is a function in a `server/` module
  that takes an `Actor`, calls `authorize(actor, "events.…")`, parses with
  `parseInput`, and throws `ServiceError`. The modules are:
  - `server/events.ts`: events, categories, and event check-in
  - `server/event-registrations.ts`: fees, registrations, and charges
  - `server/event-payments.ts`
  - `server/event-program.ts`
  - `server/event-tasks.ts`

  The `app/(app)/events/**/actions.ts` files are thin adapters. They call
  `requirePermission`, pass the `FormData` fields to the service, map an
  `invalid` error to form state (as `app/(app)/members/actions.ts` does), and
  then `revalidatePath` and `redirect`. Pages call the services directly. v1
  adds **no** `app/api/v1/events` routes, but the services are shaped so
  that adding them later is only wiring through `apiRoute`.
- **Forms** use `useActionState` and wrap each input in `<Field htmlFor>`,
  following `service-form.tsx`.
- **Every mutation is audited, in the same PR** (AGENTS.md "Every feature
  that changes data is audited"). Add the entities `event`,
  `event_category`, `event_fee`, `event_registration`, `event_payment`,
  `event_program_item`, and `event_task` to `AUDIT_ENTITIES`, and each
  phase's actions to `AUDIT_ACTIONS` (for example `event.create`,
  `event.cancel`, `event_registration.cancel`, `event_payment.record`,
  `event_payment.void`, `event_task.complete`). Wrap each write in
  `db.transaction` and call `recordAudit(tx, …)` after it, in the service.
  Each phase's integration tests assert the entry and that a failed
  validation writes none. **Event check-ins are exempt**, like
  `recordAttendance`, because `event_attendance.recorded_by` records who did
  it. Say so in the phase 1 PR.
- **Performance** (`docs/performance.md`): after `requirePermission`, each
  page makes **one** `Promise.all` batch. Derived figures (registered
  counts, paid sums, settlements) are computed in that batch's SQL
  (grouped subqueries), not with a second round trip. The sidebar item uses
  `IntentLink`. Put `bun run perf:probe` before and after numbers in each
  PR that adds a page.
- **Tables** follow `app/(app)/members/page.tsx`: `tableContext` with
  `sortKeys`, an `orderBy` that ends with `id`, `allowedValues` on every facet,
  and `overRunPage` + `redirect`.
- **Times** go through `lib/manila-time.ts`. Never call `new Date(formValue)`.
- **Money** is integer centavos, parsed and formatted only through
  `lib/money.ts`.
- **Colours** come only from tokens. `tests/ui/design-tokens.test.ts` must stay
  green.
- **Scope every id to its event.** Load child rows with
  `WHERE id = $1 AND event_id = $2`, where `$2` is the event in the URL.
  A mismatch is "not found" (spec §6, test C1).
- **Permissions:** a new key goes in `lib/permissions.ts` and in the same
  phase's migration, with grants per spec §6, following
  `docs/authorization.md`. The `events` module is **not** in
  `ROLE_ONLY_MODULES`, so a ministry can grant its keys (for example, an
  events committee or a finance team). Extend the ministry-grant tests so
  that an `events.*` grant through an active ministry reaches
  `effectivePermissions`.
- **Migrations:** `bun run db:generate --name <name>` for DDL. For
  permission and category rows, add `bunx drizzle-kit generate --custom --name
  <name>` and write the `INSERT … ON CONFLICT DO NOTHING` by hand, the way
  `0005` does. Run `bun run db:migrate` locally. Never `db:push`.
- **Checks before each PR:** `bun test lib`, `bun run test:ui`,
  `bun run lint`, `bun run build`, `bun run build-storybook`, then
  `bun run test:db:up`, `bun run test:integration` and `bun run test:e2e`, run
  one after another. The PR description lists which states were checked
  visually in Storybook.

## Phase 1: Events core

**Branch:** `feat/events-core`

- [ ] `db/seed.ts`: one upcoming one-day conference, one past fellowship

### 1.3 Validators

### 2.5 Routes and actions

- [ ] `searchMembersForPicker`: accept `events.register`, and flag members
      already registered for `eventId`.
- [ ] **Member deletion guard.** `deleteMember` in `server/members.ts` checks
      for event registrations (the foreign key is `restrict`) and throws a
      `ServiceError` ("has event registrations; mark them inactive instead")
      instead of surfacing a foreign-key violation as a 500. Test **M1**.
- [ ] Fee functions in `server/event-registrations.ts`: `addFee`,
      `updateFee`, and `setFeeActive` (a fee with registrations can only be
      deactivated). All are audited.
- [ ] `server/event-registrations.ts`, adapted by
      `app/(app)/events/[id]/registrations/actions.ts`. Every function below
      is audited inside its transaction:
    - A shared `withEventSeatLock(eventId, fn)` helper: open a transaction,
      run `SELECT … FOR UPDATE` on the event row, and pass the locked event
      and a fresh registered count to `fn` (spec §7.1). **Every seat-changing
      action uses it:** `registerMember`, `reactivateRegistration`,
      `promoteFromWaitlist`, `cancelRegistration`, and `updateEvent` when
      capacity changes. `setEventCancelled` uses it too.
    - `registerMember`: inside the lock, check `registrationState`, check
      that the fee belongs to this event and is offered, create the visitor
      member if needed (`status: "visitor"`, a `qrToken` as the members
      action does until #17 lands), and reactivate a cancelled row or insert
      a new one as `registered` or `waitlisted`. The charge is snapshotted
      from the fee.
    - `changeFee` and `adjustCharge` (`events.adjust_amount`): update the
      charge and insert a charge-history row in one transaction.
    - `cancelRegistration`: a retained amount of 0 needs `events.register`,
      and more than 0 needs `events.adjust_amount`. It never auto-promotes
      anyone.
    - `promoteFromWaitlist`: refused while full, unless `override=1` **and**
      `events.update`.
- [ ] Show the registration settings in `EventForm` and on the edit page.
- [ ] `[id]/registrations/page.tsx`: the `DataTable` (payment columns arrive
      in phase 3) and the tab in the layout, hidden only when registration is
      disabled **and** no registrations exist (**L3**).
- [ ] `[id]/registrations/new/page.tsx` and `[id]/registrations/[regId]/page.tsx`.
- [ ] Overview: add a registered/capacity stat, "N of M registered checked
      in", and the fee tiers card.
- [ ] Attendance tab: a registered or walk-in column and facet, and the
      `?show=absent` view of registered people who have not checked in
      (**K4**).
- [ ] `/events` list: add a registered/capacity column.

### 2.6 Tests

- [ ] Integration: acceptance tests **S1–S5**, **A2** (permission part),
      **A10**, **A11**, **L4**, **M1**, **AU1**, and **C1** (fees and
      registrations); plus
      re-registration reactivating the row, the visitor path creating a
      member with status `visitor`, and the permission guards.
- [ ] E2E: register an existing member, and register a new visitor.

**Done when** staff can set tiers and capacity, register members and new
visitors, and see a waitlist form at capacity, with charges snapshotted,
every charge change logged, and every seat change serialised.

## Phase 3: Payments

**Branch:** `feat/events-payments`

- [ ] `lib/event-payments.ts` + tests: `effectiveAmountDue`, `settle`,
      `paymentStatus`, and `eventFinanceSummary` (spec §3.3 and §5). Unit

- [ ] Schema: `eventPayments` (spec §4.6), with a unique `submission_id`.
      Custom migration: `events.record_payment` and `events.void_payment`,
      with grants.
- [ ] Constants: `PAYMENT_METHODS`. Validators: `paymentSchema` (a
      **positive** amount, reference required for `gcash` and

      required reason), and `voidSchema` (reason required).
- [ ] Components with stories: `payment-status-badge.tsx`,
      `payment-ledger.tsx` (voided rows struck through and marked "Voided",
      not only by colour; refunds labelled), `record-payment-form.tsx` (amount

- [ ] `server/event-payments.ts` (adapted by the registration detail's
      actions), audited: `recordPayment` (`events.record_payment`, positive
      only),
      `recordRefund` (`events.void_payment`, stores the negated amount), and
      `voidPayment`, which runs `UPDATE … WHERE voided_at IS NULL` and treats
      0 rows as "already voided". Inserts use
      `ON CONFLICT (submission_id) DO NOTHING` and return the existing row on
      a retry. The registration is loaded scoped to the URL's event. There is
      no update or delete action for payments.
- [ ] `deleteEvent`: extend the guard so that any payment row (voided
      included) or charge-history row blocks deletion (**L1**).
- [ ] Registration detail: the ledger, the charge history, outstanding or
      refund due, the payment and refund forms, and a `submission_id` hidden
      input rendered fresh on each page load.
- [ ] Registrations table: charge, effective amount due, paid,
      outstanding/refund due, and payment status columns, plus a payment
      status facet. The facet is computed with a
      grouped subquery, so the filter and sort run in SQL, not in JavaScript.
- [ ] Overview: charged, collected, outstanding, and a "Refunds due" stat
      when greater than 0, all **summed per registration**. When the event is
      cancelled, the overview also lists who is owed a refund. `/events`
      list: outstanding and refunds-due columns.
- [ ] CSV export `app/(app)/events/[id]/registrations/export/route.ts`
      (`events.view`), with one row per registration and amounts in pesos.
      Name the helper after the #26 pattern so the issue can reuse it.
- [ ] Integration: acceptance tests **A1–A9**, **L1**, **AU1**, and **C1**
      (payments).
- [ ] E2E: record a partial GCash payment and see the outstanding balance on
      the overview.

**Done when** the registration desk can take payments, admins can void or
refund them, and every balance on screen is derived from the ledger.
